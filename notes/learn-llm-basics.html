LLM の中身 — これまで動かしてきたものは何をしていたか

フェーズ 0–12 で、tokenizer → GGUF → GPU → llama-server → クラウド L4 まで一通り動かした。このノートは、その tokenize と logits の間 で何が起きているかを、実測した数字だけで説明する。フェーズ 13（姓名分割のプローブ）の前に読む。

前提: pipeline.md（BPE、chat template、temperature、KV cache、GGUF）は読んだものとして、そこにある話は繰り返さない。GPU 用語は learn-gpu-stack.html、量子化は learn-quantization.html。

1. 1 トークン分の forward を上から下まで

pipeline.md のループは「tokenize → forward で logits → sampling → detokenize → 繰り返し」だった。このノートが埋めるのは forward の箱の中である。

forward（順伝播）: 入力の token ID 列を、モデルの層を順に通して、次トークンのスコア（logits）を出す計算。推論で毎トークン走る。学習でも同じ計算をし、そのあとに逆向きのパス（backward）が足される。

箱の大きさを最初に固定する。Qwen3.5-9B（フェーズ 7 の日常）はおおよそ次の形。

部品何かQwen3.5-9B の大きさ
語彙token ID の種類数約 25 万（Qwen3.5 は 248K 級。Qwen2.5 は約 15 万）
embedding 行列ID → ベクトルの表。語彙 × d_model約 25 万行
d_model層の中を流れるベクトルの長さ（隠れ次元）数千（9B で 4096 前後。2B はフェーズ 14 で実測）
層同じ形の箱の繰り返し32 層（2B / 0.8B は 24 層）
lm_head最終ベクトル → 語彙サイズの logitsd_model × 語彙

ここで押さえるのは 2 点。層の入口と出口のベクトルは同じ長さ（だから何層でも積める）。最後に一度だけ語彙サイズに戻す（lm_head）。フェーズ 4 の /v1/models にあった n_params は、この表の全部の行列の要素数の合計である。

2. 1 層の中身: attention と FFN

1 層は 2 つの箱で、それぞれの箱の出力を 入力に足し戻す（residual 接続）。箱の前に norm（ベクトルの大きさを揃える正規化）が入る。

パラメータの大半は FFN にある。中間次元が d_model の数倍あるので、gate/up/down の 3 枚で attention の 4 枚より大きい。量子化ノートの「_M は FFN の巨大行列を薄くする」はこの話である。

2 つの箱の役割分担は「attention = どのトークンを参照するか」「FFN = 参照した内容をどう書き換えるか」と思っておけば足りる。知識（事実の記憶）は FFN 側に多く入っている、という研究結果が多い。だから LoRA を attention だけに当てるか FFN にも当てるかで、姓名の「覚え方」が変わりうる。

3. attention の 1 行と KV cache

attention は各トークン位置で 3 つのベクトルを作る。入力 x に 3 枚の重みを掛けるだけである。

  • Q（query）= x · Wq: 今の位置が「何を探しているか」
  • K（key）= x · Wk: 各位置が「何を持っているか」の見出し
  • V（value）= x · Wv: 各位置が「渡す中身」

今の位置の Q と、過去すべての位置の K の内積を取り、softmax で重みにして V を加重平均する。それに Wo を掛けて residual に足す。式は 1 行で、softmax(Q·Kᵀ / √d) · V。

これが pipeline.md の KV cache の中身である。フェーズ 3 で -c 2048 → 8192 にしたとき VRAM が 4544 → 4886 MiB に増えたのは、この保存箱を 4 倍の長さ分確保したから。重みは 1 バイトも増えていない。

GQA（grouped-query attention）: Qwen3.5-2B は attention head が Q 8 本に対して K/V 2 本。K/V を複数の Q head で共有して KV cache を小さくしている。フェーズ 14 で k_proj / v_proj の出力次元が q_proj より小さく見えたら、これが理由。バグではない。

4. Qwen3.5 の hybrid attention

ここまでの attention は「過去すべての K と Q の内積を取る」ので、計算量と KV cache が系列長に比例して伸びる。Qwen3.5 は 一部の層を Gated DeltaNet に置き換えている（hybrid）。

Gated DeltaNet: 過去を全部保存する代わりに、固定サイズの「状態」行列に畳み込んで持つ線形 attention の一種。新しいトークンが来るたびに状態を少し更新する（delta rule）。系列が長くなってもメモリが増えない。

このノートで必要なのは次の 3 点だけで、式は追わない。

  • 全層が同じ形ではない。通常 attention の層と DeltaNet の層が並んでいる。フェーズ 14 の named_modules() で、層によって線形層の名前が違って見えるのはこれ
  • DeltaNet 層にも線形層（入力を状態に写す射影）はある。LoRA をどこに当てるかを決めるとき「attention の q/k/v/o だけ」では その層を素通りすることになる。当てるか当てないかは実験条件
  • フェーズ 7 のログ「GDN は CUDA」の GDN はこれ。llama.cpp 側に専用カーネルがあるので GPU で走った

Qwen3.5 は natively multimodal（画像も同じ重みで扱う）でもある。safetensors には vision 側の重みが同梱されうる。GGUF にするときテキスト側だけを切り出す話は、フェーズ 16 で踏む。

5. 事前学習が最適化しているもの

ここまでの箱の中の数値（重み）は、どうやって決まったか。事前学習（pre-training）は、大量テキストの各位置で「次のトークンは何か」を当てるゲームを、何兆トークン分やった結果である。

cross-entropy 損失: 正解トークンにモデルが割り当てた確率 p に対して −log p。正解に確率 1 を付ければ 0、確率 0.01 なら約 4.6。全位置の平均を下げるのが学習の目的。

大事なのは、事前学習で最適化しているのは この 1 つの数字だけということ。「文法を覚えろ」「事実を覚えろ」「質問に答えろ」とは一度も言っていない。次トークンを当てる精度を上げると、結果として文法も事実も、ある程度の推論も、そこに入ってくる。

だから Base モデルは 「確率分布を出す機械」であって「答える機械」ではない。「山田太郎を姓と名に分けてください」の続きとして最もありそうなテキストが「次の問題」や「解答例: 」のような文であれば、そちらを出す。フェーズ 9 と 13 で見る「Base は続きを書く」は、壊れているのではなく、この目的関数に忠実なだけである。

6. Base と Instruct はどこが違うか

重みの 形は同じ。層数、d_model、語彙、全部同じ。違うのは 値だけである。

SFT（Supervised Fine-Tuning）: 「user の入力 → 望ましい assistant の出力」の対を、事前学習と同じ次トークン損失で学ぶ。損失は普通 assistant 側だけに掛ける（ノート B の completion-only）。
選好最適化: 同じ入力に対する「良い出力 / 悪い出力」の対や報酬で、良い方の確率を上げる。DPO、GRPO などはここ。今回の弧ではやらない。

フェーズ 9 で見た「同じ chat template を付けても Base は続きを書く」の答えはここにある。テンプレは 入力の型を揃えるだけで、「その型のあとに assistant らしい答えが来る」という確率分布は 重みの値に入っている。テンプレは Instruct が学習時に見た型と推論時の型を一致させるための約束で、Base はその約束を知らない。

thinking（<think> で先に考える）、拒否（安全のために断る）、日本語の丁寧さ、JSON だけ返す指示追従。フェーズ 7 の 3 本で見た振る舞いは全部、この事後学習で 値として入ったものである。

混同しないこと: 「Instruct = Base + system プロンプト」ではない。system プロンプトは入力側の文字列で、重みを変えない。Base に「あなたは親切なアシスタントです」と付けても、Base は「アシスタントという設定の小説の続き」を書くかもしれない。

7. 推論のコストの出どころ

1 節の縦の流れを 1 トークンごとに通る。このとき GPU は 全部の重みを VRAM から一度読む。9B Q4 なら約 5.3 GB を、1 トークンごとに。

計算そのもの（掛け算）は GPU にとって軽い。重いのは読み出しである。だから decode（1 トークンずつ生成）の速度は、おおよそ次で決まる。

decode tok/s ≈ VRAM 帯域 / 重みのバイト数
実測重み帯域（カタログ）紙上実測 Gen
フェーズ 7: 9B Q4、RTX 50605.3 GB約 448 GB/s約 85 tok/s66 tok/s
フェーズ 5: 7B Q4、RTX 50604.4 GB約 448 GB/s約 100 tok/s78 tok/s
フェーズ 5: 7B Q5、RTX 50605.1 GB約 448 GB/s約 88 tok/s69 tok/s
フェーズ 11: 27B Q4、L416 GB約 300 GB/s約 19 tok/s14.5 tok/s

紙上の 7–8 割に実測が落ちるのは、KV cache の読み書きや層間の待ちがあるため。それでも 並びは帯域 / バイト数で説明できる。Q5 が Q4 より遅いのは「計算が重い」のではなく「読むバイトが多い」から。

フェーズ 7 の 27B（-ngl 30、3.7 tok/s）が極端に遅いのは、GPU に載らない層を CPU が処理し、CPU 側の RAM 帯域（数十 GB/s）で残りの重みを読んでいるから。-ngl を 32 以上にして VRAM が 7880 MiB で頭打ちになり decode が落ちたのは、GPU 側で溢れたデータのやり取りが増えたため。

一方 prompt eval（入力の一括処理）は速い。フェーズ 7 の 9B で約 188 tok/s、L4 の 27B で 83.9 tok/s。プロンプトの全位置を 1 回の forward でまとめて通せるので、重みを 1 回読めば何百トークンも処理できる。decode は 1 トークンごとに読み直すので、ここに差が出る。

学習（フェーズ 15）はこの forward に backward が足される。1 ステップで重みを読み、活性化を保存し、勾配を計算して optimizer を回す。読むバイト数は推論より多く、VRAM には重み以外に活性化・勾配・optimizer 状態が乗る。その算数は ノート B の 2 節。

8. 確認問題

Q1. Qwen3.5-9B を bf16（1 重み 2 バイト）でそのまま置くと何 GB か。8GB GPU に載るか。

約 9 × 10⁹ × 2 バイト ≈ 18 GB。載らない。Q4_K_M（実測 5.3 GB）にして初めて載る。フェーズ 14 で 2B を bf16 で読むときは 約 4 GB で、これは載る。

Q2. Base モデルに Instruct と同じ chat template を付けて推論すると、Instruct と同じように答えるか。

答えない。テンプレは入力の型を揃えるだけで、「その型の続きに assistant らしい答えが来る」という分布は重みの値に入っている。Base はその値を持っていないので、続きを書く（フェーズ 9 / 13 の実測）。

Q3. -c 2048 から -c 8192 にすると VRAM が増える。増えたのは重みか、KV cache か。

KV cache。重みはコンテキスト長と無関係で 1 バイトも増えない。フェーズ 3 で 7B Q4 が 4544 → 4886 MiB になった +342 MiB は、層ごと・位置ごとの K と V の保存箱を 4 倍確保した分。

Q4. 同じ RTX 5060 で 7B Q4 が 78 tok/s、Q5 が 69 tok/s。Q5 が遅いのは計算が重いからか。

違う。decode 速度はおおよそ「帯域 / 重みのバイト数」で決まり、Q5 は読むバイトが約 15% 多い（4.4 → 5.1 GB）。計算量はほぼ同じ。

Q5. 事前学習で最適化している量は何か。「質問に答える能力」はどこで付くか。

次トークンの cross-entropy 損失（正解トークンの −log p の平均）だけ。「質問に答える」は事後学習（SFT → 選好最適化）で、user / assistant の対を同じ損失で学ぶことによって、重みの値として付く。
