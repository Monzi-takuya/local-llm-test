量子化は何をしているか

答えの文章を圧縮しているのではない。重み（モデルが覚えた数値の行列）を、少ない bit で近似して VRAM に載せている。フェーズ 5 の Q4 vs Q5 はこの話の実測。

このマシン: RTX 5060 8GB。実測は results/05-bench.md。

1. 何を量子化するか

重み（weight）は、Transformer の各層にある大きな数値の表である。学習の結果として固定され、推論ではほぼ読み取り専用。トークンを 1 個進めるたびに、この表と入力のベクトルを掛け合わせる。

量子化（quantization）は、その表の各数値を「少ない bit の整数 + 小さな補正」で表す変換である。JPEG のように生成文を潰す処理ではない。tokenizer の語彙 ID も変えない。

混同しないこと: temperature は次トークンの選び方。Q4 は重みの保存形式。両方とも「雑になる」方向に見えるが、層が違う。温度は毎回のサンプル、量子化はファイルに焼き付いた近似。

2. なぜ 7B の FP16 は 14GB か

パラメータ数は重みの個数。Qwen2.5-7B は約 7.6×109 個（フェーズ 4 の /v1/models では n_params 7615616512）。

1 個を何バイトで持つかが、だいたいのファイルサイズになる。

形式1 重み7.6B の概算8GB GPU
FP324 バイト≈ 30 GB載らない
FP16 / BF162 バイト≈ 15 GB載らない
Q8_0（約 8bit）≈ 1 バイト≈ 8 GB重みだけで満杯。KV cache が残らない
Q5_K_M≈ 5.5 bit実測ファイル 5.1 GB載る（この検証 5204 MiB）
Q4_K_M≈ 4.5 bit実測ファイル 4.4 GB載る（この検証 4544 MiB）

「4bit」は正確に 0.5 バイト/重みではない。後述の scale（補正用の小さい浮動小数）と、層によって bit 数を変えるため、Q4_K_M は 4.0 bit より少し重い。

3. ブロックごとの近似（scale + 整数）

よく使うのは、重みを 32 個くらいの ブロックに切り、ブロック内の最大値から scale を 1 つ決める方法である。

ブロックを跨いで 1 つの scale にすると、大きい値に引っ張られて小さい値が潰れる。だから「全部を 4bit 整数にする」のではなく、近くの重み同士で物差しを共有する。

4. Q4_K_M / Q5_K_M の中身

llama.cpp の K-quant は、上のブロックをもう一段まとめた形式である。

  • super-block: 256 個（32×8）をまとめて、scale の持ち方を工夫する
  • Q4_K: 本体は 4bit 整数。Q5_K は 5bit。残りの bit で誤差を減らす
  • _S / _M / _L: 同じ「Q4」でも、どの層を厚く残すかが違う。_M（Medium）は注意層や出力付近を少し厚くし、FFN の巨大行列を薄くすることが多い

だからファイル名の Q4_K_M は「全部が均一 4bit」ではない。混在量子化（tensor ごとに bit 数が違う）である。埋め込みや出力層は Q6 寄りのまま、巨大な中間層だけ Q4、という配分が典型。

Hugging Face 上の bartowski などの GGUF は、層の重要度（importance matrix / imatrix）を測ってから bit を振り分けることがある。同じ「Q4_K_M」でも、誰が作ったファイルかで中の割り当てが少し違う。

Q5 は Q4 より整数の段階が細かい（32 段階 → 32 超）。同じ super-block 構造なので、ファイルはだいたい「Q4 + 1bit 分」重くなる。このマシンでは 4.4G → 5.1G。

5. 推論時は「戻して掛ける」

VRAM に載っているのは量子化済みの整数 + scale である。計算のたびに FP16 の完全なコピーを作って置き直すのではない。

CUDA カーネル（GPU 上の小さなプログラム）が、掛け算の直前にブロック単位で ŵ = q × scale をレジスタに戻し、すぐ行列積に使う。これを on-the-fly dequant と呼ぶ。

速度の主役は計算コアの理論 FLOPS より、重みを VRAM から読む帯域であることが多い。decode（1 トークンずつ）は特にそう。だから bit を増やすと、品質の余地と引き換えに tok/s が落ちうる。

6. 量子化しないもの

  • KV cache: 生成中に溜まる Key/Value。既定では FP16 寄り。コンテキストを伸ばすとここが増える（フェーズ 3/5 の -c 2048 → 8192 で +342 MiB）。重みの Q4/Q5 とは別口座
  • 活性化（activation）: 層を進む途中のベクトル。計算の作業領域で、GGUF の Q4 とは別
  • tokenizer: 語彙とマージ規則。量子化しても ID の意味は同じ

だから「Q4 にしたからコンテキストも 4bit」ではない。8GB の内訳は 重み + KV cache + ランタイム。

7. 品質が落ちる場所

復元した ŵ は元の w と少し違う。その誤差が行列積を通り、logits（次トークンの生スコア）を少し動かす。

temperature 0（argmax、最大スコアの ID だけ取る）でも、1 個目のトークンがずれると、その先の文は全部変わる。フェーズ 5 の日本語では、同じ Qwen 7B でも Q4 はきれいな一文、Q5 は英中が混ざった。これは「Q5 が常に悪い」ではなく、greedy 1 本では誤差の出方がプロンプト依存という実測である。

英語プロンプトでは Q4 と Q5 がほぼ同じ文だった。最初の数トークンの logits が、こちらでは同じ argmax に落ちた。

GPU と CPU でも、同じ Q4 ファイル・同じ seed・同じ temp 0 で日本語が一致しなかった。カーネルの加算順で浮動小数の末尾が違い、argmax が割れることがある。品質比較は「同じデバイス・同じ量子化」で揃える。

8. この検証の数字

7B Instruct、GPU 全載せ、-c 2048。生成中 VRAM 最大: Q4_K_M 4544 MiB / Q5_K_M 5204 MiB。Generation: Q4 約 78 tok/s、Q5 約 69 tok/s。差分は重みの厚さ（帯域）と一致する。8GB（8151 MiB）にはどちらも載った。Q8 は重みだけで余裕が無いので省略。
