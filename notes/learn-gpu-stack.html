1. llama.cpp とは

llama.cpp は、GGUF という形式のモデルファイルを読み、token ID を GPU（または CPU）で次のトークンに進める 推論エンジン である。チャットアプリでもクラウドでもない。C++ で書かれたプログラム群（llama-cli、llama-server など）の総称として使っている。

Ollama は、そのエンジンを中に隠し、モデルの download と localhost:11434 の HTTP を足した箱である。フェーズ 2 で日本語が出たのは Ollama 経由。フェーズ 3 は箱を外して、同じ系統の計算を llama-cli で直接回した。

混同しないこと: モデル名（Qwen2.5-7B）は「何を考えるか」。llama.cpp は「どう計算するか」。同じ Qwen を Ollama でも llama.cpp でも回せる。フェーズ 1 の tokenizer だけとも別で、あちらは重みを載せていない。

1b. イメージ: llama-cli + GPU ベンダ実装でモデルを動かす

そのイメージで合っている。 ただし部品は 2 つではなく 4 段に分けると、フェーズ 3 の symlink が意味を持つ。

  1. モデル（GGUF）… 重み。考えの中身。
  2. llama-cli… 進行役。tokenize、何層やるか、-ngl、sampling。GPU の機種知識は持たない。
  3. llama.cpp 側のベンダ実装（libggml-cuda.so など）… 「CUDA の言葉で行列を GPU に投げる」コード。NVIDIA 用 / AMD 用で別ファイル。
  4. GPU ベンダのドライバ… カードそのものを動かす特権側。この PC では Windows に入っている NVIDIA ドライバ。

3 が「llama.cpp が書いた CUDA 用プラグイン」、4 が「NVIDIA が書いた本物のドライバ」。両方とも広義の「GPU ベンダ側の道」だが、入れた場所が違う。3 は WSL のファイル（Ollama 同梱）、4 は Windows。

2. ~/opt は「opt ファイル」ではない

Linux の慣習で、/opt やホームの ~/opt は 配布物のプログラムを置くディレクトリ である。拡張子 .opt のファイル形式ではない。コンパイラの最適化オプション -O2 とも無関係。

対して ~/models は モデル本体（GGUF） を置く場所。プログラムとデータを分けているだけ。Excel 本体が C:\Program Files にあり、xlsx がドキュメントフォルダにあるのと同じ切り方。

~/opt/llama.cpp/llama-b10938/llama-cli \
  -m ~/models/Qwen2.5-7B-Instruct-Q4_K_M.gguf \
  -ngl 99 -c 2048 -n 64 -p "…"

1 行目が「どのエンジンで」、-m が「どの脳で」。エンジンは 1 つで、モデルファイルを差し替えれば Qwen にも Gemma にもなる。逆に、Gemma の GGUF を Qwen 用だと思って読ませても動かない（中の tokenizer / 層の形が違う）。

Ollama の実体は /usr/share/ollama に別管理される。フェーズ 3 ではそれを変換せず、Hugging Face の GGUF を ~/models に置いた。同じ「7B Q4」クラスでも、ファイルは別物。

3. .so ファイルとは

.so（shared object）は、Linux の 共有ライブラリ である。Windows の .dll、macOS の .dylib に相当する。「単体では起動しないが、実行ファイルが必要になったらメモリに載せる部品」。

llama-cli 本体は「GGUF を読んで推論する枠」である。NVIDIA 向けの GPU カーネル全部を 1 本の実行ファイルに焼き込むと巨大になり、AMD 機では無駄になる。そこで GPU ベンダごとの実装を libggml-cuda.so や libggml-vulkan.so に分け、起動時に隣のファイルを探す。

LD_LIBRARY_PATH は「.so をどのフォルダから探すか」を足す環境変数。フェーズ 3 では次を付けた。Ollama が既に持っていた CUDA 用 .so と、その依存（libcudart など）を llama-cli から見えるようにするため。

export LD_LIBRARY_PATH="$BIN:/usr/local/lib/ollama/cuda_v13:/usr/lib/wsl/lib"
ln -sfn /usr/local/lib/ollama/cuda_v13/libggml-cuda.so "$BIN/libggml-cuda.so"

ln -sfn はコピーではなく symlink（別名）。実体は Ollama 側にあり、llama-cli の隣に「CUDA 用部品はここ」と指しているだけ。新規ライブラリを apt で入れたわけではない。

--list-devices が (none) なら、実行ファイルはあるが GPU 用 .so が載っていない / その道のドライバが無い。Vulkan 版公式バイナリがまさにこれだった。

4. CUDA とは

CUDA は NVIDIA が作った、GPU を汎用計算に使うための仕組み（API + コンパイラ + ランタイム）である。ゲームの「絵を描く」だけでなく、行列計算を GPU に投げられる。LLM の forward（層を通して次トークンのスコアを出す計算）はまさにその用途。

名前が混ざるので、役割を 3 つに分ける。

層何をするかこのマシン
ドライバ OS から GPU を触る土台。Windows 側に入り、WSL からは /dev/dxg と libcuda.so で見える あり（nvidia-smi 成功）。Linux 用 NVIDIA ドライバは入れない
ランタイム .so アプリが CUDA を呼ぶときの共有ライブラリ（libcudart、libcublas、libggml-cuda.so） Ollama が /usr/local/lib/ollama/cuda_v13/ に同梱
Toolkit（nvcc） CUDA のコードを 自分でコンパイルするための開発ツール 未導入。ソースから llama.cpp をビルドするときだけ必要。入れる前に確認する

「CUDA が見える」＝ nvidia-smi が GPU を出すこと。「llama.cpp が CUDA で計算している」＝ libggml-cuda.so が載り、--list-devices に CUDA0 が出ること。前者だけだと、エンジンが CPU に落ちることがある（フェーズ 3 の比較対象）。

実測: CUDA0: NVIDIA GeForce RTX 5060。compute capability 12.0（Blackwell）。古いバイナリは GPU を列挙できても中のカーネルが 12.0 を知らず、CPU 並みの速度になる。

4b. なぜ Windows 側の CUDA ドライバを使うか

GPU というハードウェアを握っているのが Windows だから。 WSL2 は Linux ディストロだが、PCIe の RTX 5060 をカーネルが直接所有しているのはホスト OS（Windows）である。Linux 用 NVIDIA ドライバを WSL の中に入れると、同じカードを二重に取り合う形になり、公式にも「入れるな」とされている。このリポジトリの制約もそれ。

では WSL の nvidia-smi や libcuda.so は何か。それは Windows ドライバへの橋 である。実体は /usr/lib/wsl/lib/（Microsoft が配る WSL GPU 用ライブラリ）。呼び出しはだいたい次の順。

WSL の llama-cli
  → libggml-cuda.so（計算の中身）
  → libcudart / libcuda.so（CUDA の入口）
  → /dev/dxg（WSL が GPU を見せるデバイス）
  → Windows の NVIDIA ドライバ
  → RTX 5060

だから「WSL から CUDA を使う」＝ Linux にドライバを新規インストールする、ではない。Windows に入っているドライバ（このマシンでは nvidia-smi の KMD 610 系）を、橋経由で借りる。

入れる入れない
GPU を動かす土台 Windows の NVIDIA ドライバ（GeForce アプリ等で更新） WSL 内の Linux 用 NVIDIA ドライバ
アプリが CUDA を呼ぶ部品 Ollama 同梱の .so、または（必要なら）CUDA Toolkit ドライバの代わりに Toolkit だけ入れる、は不可

Vulkan 公式バイナリがデバイス 0 件だったのも同じ地図で読める。橋として配られているのが今回は CUDA 用（libcuda.so）で、NVIDIA の Vulkan ICD は WSL 側に無かった。ハードウェアは 1 枚、見える API はドライバと橋の組み合わせで決まる。

5. Vulkan / ROCm / SYCL は「CUDA の代わりの道」

GPU 計算の道は CUDA 一本ではない。llama.cpp は バックエンド（実際に計算する実装）を差し替えられる。GitHub Releases に ubuntu-vulkan / ubuntu-rocm / ubuntu-sycl と並んでいたのは、「同じ llama-cli でも、中で読む .so が違う」という意味。

Vulkan

Vulkan は Khronos という業界団体の、GPU 向け低レベル API である。NVIDIA / AMD / Intel が実装を出せる「共通の差し込み口」。グラフィックスで有名だが、計算にも使える。llama.cpp の Ubuntu Vulkan ビルドは libggml-vulkan.so を同梱する。

実際に GPU を使うには、OS 側にそのベンダの ICD（Installable Client Driver。Vulkan の実装ファイル）が要る。フェーズ 3 で --list-devices が空だった理由は、WSL に NVIDIA の Vulkan ICD が無く、intel/radeon/nouveau の json だけがあったから。CUDA の libcuda.so があることと、Vulkan が見えることは別。

ROCm

ROCm は AMD の GPU 計算スタックで、CUDA に相当する位置づけ。Radeon 向け。この PC の計算 GPU は GeForce なので、ROCm ビルドを入れても RTX 5060 は加速しない。

SYCL

SYCL は Khronos の C++ 向け抽象で、「同じコードから複数のアクセラレータを狙う」ためのもの。Intel の oneAPI 経由でよく使われる。llama.cpp の SYCL ビルドは主に Intel GPU 向けの選択肢。この検証の主戦力ではない。

名前一言誰の GPUこの検証
CUDANVIDIA の計算 APIGeForce / RTX採用。80 tok/s
Vulkanベンダ横断の GPU APIICD があるもの公式バイナリはデバイス 0 件

6. -ngl とは

LLM の本体は Transformer で、同じ塊（層 / layer）が何十段も積み上がっている。7B 級なら数十層。各層は巨大な行列乗算なので、VRAM に置けるなら GPU でやる方が速い。

-ngl（n GPU layers）は そのうち何層を GPU（VRAM）に置くか の整数。残りは CPU とホスト RAM。

  • -ngl 0 … 全層 CPU。GPU は（ほぼ）使わない
  • -ngl 99 … 層数が 99 未満なら実質すべて。よく使う「全部載せ」
  • 中途半端な数 … 8GB に全載せできない大きなモデルで、入る分だけ GPU、残り CPU（この検証の 7B Q4 では不要）

Ollama の PROCESSOR 100% GPU は、中でこれに近い全載せをしている、と読んでよい。ただし Ollama では -ngl を自分で数字指定しにくい。フェーズ 3 の目的は、その数字を手で動かして速度差を見ることだった。

隣のレバー -c（コンテキスト長）は層の置き場ではなく、何トークン分の過去を残すか。残すのが KV cache で、長いほど VRAM が増える。実測では -c 2048 で 4544 MiB、8192 で 4886 MiB。
