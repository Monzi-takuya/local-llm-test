1. 学習とは何を動かすことか

推論は「重みを固定して forward を回す」だった。学習は「forward のあとに 正解との差を測り、その差が小さくなる方向に 重みを少し動かす」を繰り返す。1 バッチ分の流れは次の 4 段。

勾配（gradient）: loss を各重みで偏微分した値。「この重みを少し増やすと loss がどれだけ動くか」。重みと同じ形の行列になる。
learning rate（lr）: 勾配の方向にどれだけ動かすかの係数。LoRA では 1e-4 〜 2e-4 が慣習。大きすぎると発散、小さすぎると動かない。
AdamW: 勾配の移動平均（m）と二乗の移動平均（v）で 1 重みごとに歩幅を調整する optimizer。重みごとに 2 つの状態を持つ。

ノート A の 5 節と同じ loss（cross-entropy）を使う。事前学習も SFT も、最適化している量は同じ。違うのはデータ（何兆トークンの生テキストか、100 件の user / assistant 対か）と、どの位置の loss を数えるか（4 節）。

2. なぜ全パラメータ学習は 8GB に載らないか

推論の VRAM 算は 量子化ノート で「重み + KV cache + ランタイム」だった。学習では 1 節の 3 と 4 のぶんが乗る。2B を素直に全部学習する場合。

乗るもの形2B・bf16 のとき
重み W全パラメータ × 2 バイト約 4 GB
勾配重みと同じ形 × 2 バイト約 4 GB
AdamW の m と v重みと同じ形 × 2 枚 × 4 バイト（fp32 で持つのが普通）約 16 GB
活性化seq × batch × d_model × 層数 × …seq 256・batch 4 なら数百 MB 〜 1 GB
合計約 24 GB 超。RTX 5060 8GB に載らない

重み 4 GB は載るのに、学習にすると 6 倍になる。「動かす重みの数」がそのまま勾配と optimizer 状態の量になるのが理由。ここから、「動かす重みを減らせば載る」という発想が LoRA（5 節）になる。

推論の Q4 GGUF（2B なら約 1.3 GB）は学習に使えない。Q4 は整数 + scale の保存形式で、勾配を流す先の連続値の重みではない（量子化ノート 3 節）。学習は Hugging Face の bf16 safetensors から始め、終わってから Q4 に戻す（8 節）。QLoRA は「本体を 4bit で凍らせて LoRA だけ学ぶ」方式で、これは載るが今回はやらない（9 節）。

3. SFT: 対を 1 本の token 列にする

学習データは「user の入力」と「望ましい assistant の出力」の対。だがモデルに入るのは 1 本の token 列である。chat template で繋いで tokenize する。

<|im_start|>user
次の日本人の氏名を姓と名に分け、JSON だけを返してください。キーは sei と mei。説明は不要です。
氏名: 山田太郎<|im_end|>
<|im_start|>assistant
{"sei":"山田","mei":"太郎"}<|im_end|>

フェーズ 1 で「14 トークンの文がテンプレで 43 トークンになる」を見た。SFT の 1 サンプルはあの 43 トークン相当の列に、答えの JSON（10 トークン前後）と終端 <|im_end|> を繋いだもの。全体で 60–70 トークン。seq 256 で十分に収まる。

推論時のテンプレと学習時のテンプレは 同じ文字列でなければならない。Instruct が学習時に見た型と推論時の型が一致していることが、指示追従の前提だった（ノート A 6 節）。フェーズ 15 では apply_chat_template(..., tokenize=False) を print して、フェーズ 13 のプロンプトと同じかを目で確認する。

Qwen3.5 のテンプレは non-thinking でも空の <think></think> を assistant 側に差し込むことがある。それがプロンプト側に入るか答え側に入るかで、次の節のマスクの範囲が変わる。

4. completion-only loss

1 本の token 列のどの位置で loss を数えるか。事前学習は全位置。SFT では普通、答え側だけ。

PyTorch の cross-entropy は、正解 label に -100 が入っている位置を 無視する。だから「プロンプト側の label を全部 -100 にする」だけで、答え側だけに勾配が流れる。

なぜプロンプト側を外すか。外さないと、モデルは「次の日本人の氏名を姓と名に…」という プロンプトの文面を当てることにも勾配を使う。100 件全部に同じ文面があるので、そこは 1 epoch で完全に暗記され、loss の大半をプロンプト暗記が占める。答えの JSON を学ぶ信号が薄まる。

終端 <|im_end|> を緑に含めるのも大事。含めないと「JSON を出したあとに止まる」ことを学ばず、生成が続いてしまうモデルになる。

ここが 手法確認の中心。Unsloth や高レベル API はこのマスクを自動でやってくれるが、やってくれた結果を見なければ「SFT を理解した」とは言えない。フェーズ 15 の合格条件に「labels の decode に user 文が無い」を入れているのはそのため。

5. LoRA: 凍らせて、小さな差分だけ学ぶ

2 節の算数で、動かす重みの数がそのまま VRAM になった。LoRA は「元の重み W は凍らせて（勾配を計算しない）、小さな差分だけを学ぶ」方式。

LoRA（Low-Rank Adaptation）: 重み W（d_out × d_in）に対して、W' = W + (α / r) · B·A とする。A は r × d_in、B は d_out × r。学習するのは A と B だけ。r（rank）は 4〜64 程度の小さい数。α（alpha）はスケール係数で、慣習的に α = 2r。

2 節の算数に戻す。動かすのは A と B だけなので、勾配も AdamW の m と v も A と B の分だけ。W は bf16 のまま読み取り専用で 4 GB。

乗るもの全パラメータ学習LoRA（r=8、全線形層に当てて数 M 個の場合）
重み W4 GB4 GB（凍結。bf16 のまま）
勾配4 GB数 MB 〜 数十 MB
AdamW m, v16 GB数十 MB
活性化〜1 GB〜1 GB（backward のためにこれは残る）
合計約 24 GB約 5–6 GB。8GB に載る

活性化が残るのは、backward で A と B の勾配を出すために forward 途中の値が要るから。ここが seq と batch で伸びる。8GB を超えたときに「batch 1 → seq 短縮 → gradient checkpointing（活性化を捨てて backward 時に再計算する）」の順で削るのは、この行を削っている。

初期値は B = 0、A は乱数。学習開始時点で B·A = 0 なので、LoRA を付けた直後のモデルは元と完全に同じ出力。ここから差分が育つ。フェーズ 15 の「学習前 bf16」の列は、この状態と一致するはず。

print_trainable_parameters() が出す「trainable params / all params / trainable%」は、この表の左列と右列の比。r=8 で 7 種の線形層に当てると全体の 1% 未満が典型。フェーズ 15 でこの数字を書き、11 節の Q3 を自分の手で検算する。

6. どの層に当てるか（target_modules）

LoRA は「この名前の線形層に B·A を足す」と指定する。ノート A 2 節の 7 つの名前が候補。

グループ名前何をしている層か当てる意味
attentionq_proj k_proj v_proj o_projどの位置を参照するか、参照した内容をどう混ぜるか「氏名: の直後を見る」「姓の切れ目を見る」のような 参照の仕方 を調整

Gated DeltaNet 層（フェーズ 14 で実測。in_proj_* / out_proj 系の見込み）過去を固定サイズの状態に畳む線形 attentionattention の 4 つの名前だけ指定すると この層は素通りする。含めるかは実験条件

なぜ「名前で選ぶ」という操作が要るか。peft の既定はよく知られたアーキテクチャの名前を知っているが、Qwen3.5 のように 層ごとに構造が違うモデルでは、既定が一部の層を取りこぼす。named_modules() で全部の線形層を列挙し、どの名前が何層にあるかを自分で確認する。それがフェーズ 14 の本体。

7. 過学習と破滅的忘却

100 件で LoRA を足すと、出力の分布が「姓名 JSON 側」に寄る。寄せ方が強いと、2 種類の副作用が出る。同じ機構から出るので、片方だけ避けるのは難しい。

フェーズ 15 でこれを どちらが先に出るかとして観察する。100 件・epoch 3 は普通に考えて両方出る設定で、それを見るのが目的。合格は精度ではなく、「e1 では型だけ付いて忘却は無かった」「e3 で held-out が落ちて q-ja が JSON になった」のような 差の記録。

本番でこれを避けるには、一般的な会話データを混ぜる（忘却対策）、held-out で早期停止する（過学習対策）、rank と lr を下げる、などがある。今回は 避けない。見えないと理解できないから。

8. merge と量子化

学習が終わると、手元にあるのは「元の W（bf16、4 GB）」と「A, B（数十 MB の adapter）」。llama.cpp で動かすには 2 つの道がある。

道 1 で気にする点。B·A は 小さい値の足し込みで、Q4 は重みを 32 個ブロックの scale で丸める（量子化ノート 3 節）。差分がブロックの丸め幅より小さければ、Q4 化で差分が一部消える可能性がある。adapter 直後（bf16）と merge → Q4 で held-out の結果を並べるのは、これを見るため。1–2 件のずれは丸め、10 件ずれるなら merge かテンプレの問題。

道 2 は本体を Q4 のまま、差分を bf16 で持つ。丸めの入り方が違うので、道 1 と結果が微妙に違いうる。速度は少し落ちる（毎トークン A, B の計算が足される）。

merge の順序は bf16 で足してから量子化。Q4 にしてから足すことはできない（Q4 は整数 + scale で、足し算の対象になる連続値ではない）。

10. 混同ポイント

  • Word2vec の追加学習と LoRA: Word2vec は語彙ベクトルを足す・更新する。LoRA は語彙側（embed_tokens）を触らず、層の中の線形層に差分を足して 生成分布を対でずらす。「山田」のベクトルが変わるのではなく、「氏名: 山田太郎 の続きに何が来るか」の確率が変わる
  • KV cache と label マスク: KV cache は推論で過去の K, V を保存して計算を省く仕組み。label の -100 は学習でどの位置の loss を数えるかの指定。両方「位置ごとに何かを持つ」が、片方は速度、片方は勾配の話
  • temperature と learning rate: 両方「どれだけ動くか」に見える。temperature は推論時に分布をならす係数で、重みは変えない。lr は学習時に重みを動かす歩幅で、推論には残らない
  • Q4 の重みと学習用の重み: 同じ「Qwen3.5-2B」でも、GGUF Q4 は推論専用の保存形式、safetensors bf16 は学習の入口。相互に変換できるが、Q4 → bf16 は精度が戻らない
  • adapter を付けた直後 = 学習前: B が 0 で初期化されるので、付けた時点では元と同じ出力。「LoRA を付けたら変わった」は学習の結果であって、付けたこと自体の効果ではない

11. 確認問題

Q1. 2B を bf16 で全パラメータ学習すると VRAM はいくら要るか。内訳は。

重み 4 GB + 勾配 4 GB + AdamW の m, v（fp32）16 GB + 活性化 ≈ 24 GB 超。8GB に載らない。LoRA では勾配と m, v が A, B の分だけになり、約 5–6 GB。

Q2. completion-only を外して全位置に loss を掛けると何が起きるか。

100 件で共通のプロンプト文面を当てることに勾配が使われ、そこは 1 epoch で暗記される。loss の大半をプロンプト暗記が占め、答えの JSON を学ぶ信号が薄まる。加えて「氏名: 」の続きにプロンプト文を生成し始めることがある。

Q3. d_in = d_out = 2048 の線形層に rank 8 の LoRA を当てると、増えるパラメータは何個か。元の何 % か。

A: 8 × 2048 = 16,384、B: 2048 × 8 = 16,384、合計 32,768。元は 2048² = 4,194,304 なので約 0.78%。FFN の中間次元が大きい層では d_in と d_out が違うので、r × (d_in + d_out) で計算する。

Q4. LoRA を付けた直後（学習 0 step）のモデルの出力は元と違うか。

同じ。B が 0 で初期化されるので B·A = 0。出力の違いは学習で B が育った結果。

Q5. train の名前は 19/20 当たるが held-out は 10/20。「こんにちは」には普通に返す。これは過学習か、忘却か。

過学習（train と held-out の差が大きい）。忘却はまだ出ていない（会話が壊れていない）。epoch を増やす、lr を上げると忘却も出てくる可能性がある。

Q6. LoRA の差分を Q4 GGUF に入れるには、量子化してから足すか、足してから量子化するか。

足してから量子化。Q4 は整数 + scale の保存形式で、足し算の対象にならない。bf16 で W + (α/r)·B·A を計算し、その結果を f16 GGUF → Q4_K_M にする。差分が丸め幅より小さいと一部消えうるので、adapter 直後と Q4 化後を同じ 20 件で比べる。
